## 1. 아키텍처 및 코드 구조
* **계층형 아키텍처(Layered Architecture) 준수**: Controller(표현), Service(비즈니스 로직), Repository/Data Access(데이터), DTO(데이터 전송) 단계를 엄격히 분리한다. Service 레이어는 인프라나 HTTP 스펙(Req, Res)에 의존해서는 안 된다.
* **단일 책임 원칙(SRP)**: 하나의 클래스/함수는 하나의 기능만 담당한다. 비즈니스 로직이 길어지면 작은 단위의 도메인 서비스나 헬퍼 함수로 추출한다.

## 2. 보안 및 데이터 보호
* **민감 정보 보호**: API Key, 비밀번호, 인증 토큰, SMS 발송 크레덴셜 등은 절대 코드에 하드코딩하지 않는다. 반드시 환경 변수(`process.env` 또는 `.env`)를 사용하도록 코드를 작성한다.
* **입력값 검증(Validation)**: 외부에서 들어오는 모든 요청 파라미터(Body, Query, Path)는 진입 단계(Controller/DTO)에서 유효성 검사를 강제한다. (예: 폰 번호 형식, 필수 값 누락 등)

## 3. 에러 핸들링 및 로깅
* **예외 처리**: `try-catch` 블록은 단순히 에러를 삼키지 않고, 의미 있는 커스텀 에러 객체를 던지거나 명확한 HTTP 상태 코드로 변환해야 한다.
* **로깅 스탠다드**: 시스템의 상태 변화(인증 요청, 인증 완료, 외부 API 호출 실패 등)가 발생할 때 반드시 레벨별 로깅(`info`, `warn`, `error`)을 포함한다. 민감한 개인정보(예: 인증번호 원본)는 로그에 남기지 않는다.

## 4. 프로젝트 명세서(system-spec.md) 동기화 규칙
* **명세서 최신화 의무**: 새로운 라이브러리(의존성)를 추가하거나, 새로운 도메인/엔티티/API 엔드포인트를 구현하거나, 폴더 구조를 변경할 때는 **반드시** 루트의 `system-spec.md` 파일을 함께 업데이트해야 한다.
* **코드 수정과 문서 수정의 동시 적용**: 코드를 다 고치고 나서 마지막 단계에 `system-spec.md` 파일에 변경 내역을 반영하고, 어떤 부분이 업데이트되었는지 사용자에게 요약 보고한다.
